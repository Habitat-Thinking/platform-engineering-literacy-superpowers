# Quick Scan Rubric

For each dimension, read all five level descriptors and select the one that
best describes what you can *consistently* do today. Not your best day. Not
what you could do with help. The level where you operate reliably.

If you find yourself between two levels, choose the lower one — the one you
can do without thinking. The higher one is your growth edge.

## Context Awareness

*Can you see the system — its users, needs, pain points, strategic landscape,
and organisational dynamics?*

| Level | Descriptor |
| ----- | ---------- |
| Level 0 — Aware | I can articulate what problem my platform solves (or should solve) in one sentence, without mentioning a specific technology. I can draw a rough picture of who the platform's users are and what they need from it. |
| Level 1 — Explorer | I can produce a Wardley Map of my platform landscape that a stakeholder finds insightful. I can build a multi-lens map (combining user needs, value streams, and systems thinking) for a specific developer workflow. When someone proposes a platform change, I instinctively ask about user needs and stakeholder perspectives before discussing implementation. |
| Level 2 — Designer | I can translate mapped context into specific design decisions — I can show how a finding from a Wardley Map or value stream map led to a concrete platform design choice. I evaluate platform features against the context they will operate in, not just their technical merits. |
| Level 3 — Engineer | I can maintain living context systems — maps, models, and feedback loops that evolve continuously rather than being produced once and forgotten. My strategic decisions are informed by regularly updated situational awareness, not point-in-time analysis. |
| Level 4 — Steward | I can cultivate context awareness across the organisation — teaching others to map, facilitating cross-team strategic conversations, and establishing practices that keep situational awareness current even when I am not in the room. |

## Cognitive Load Design

*Can you design platform experiences that reduce extraneous load and support
developer flow?*

| Level | Descriptor |
| ----- | ---------- |
| Level 0 — Aware | I can identify at least three sources of extraneous cognitive load in my current developer experience. I understand the difference between intrinsic complexity (the problem is genuinely hard) and extraneous load (the tooling makes it harder than it needs to be). |
| Level 1 — Explorer | I can diagnose cognitive load using structured techniques — I can trace a developer workflow step by step and identify where representational state is lost, where context-switching is forced, and where unnecessary complexity is introduced. |
| Level 2 — Designer | I can design platform features that measurably reduce cognitive load. I evaluate every proposed feature against the question "does this add or reduce cognitive load?" and I can articulate the answer with specifics, not generalities. I apply the 4pm Friday test — evaluating platform experiences against worst reasonable conditions. |
| Level 3 — Engineer | I can measure cognitive load quantitatively and qualitatively — through developer surveys, workflow timing, error rates, and direct observation. I use these measurements to prioritise platform work, not just intuition. |
| Level 4 — Steward | I can sustain cognitive load management as an organisational practice — it is embedded in how we evaluate platform changes, not dependent on my personal advocacy. Teams across the organisation consider cognitive load as a design constraint without being prompted. |

## Pattern Application

*Can you apply the Platform Pattern Language appropriately to your context?*

| Level | Descriptor |
| ----- | ---------- |
| Level 0 — Aware | I can name the ten platform patterns (Golden Path, Self-Service, Abstraction, Composability, Guardrails, Verification Infrastructure, Observability, Extensibility, Incremental Rollout, Team API) and describe the intent of each in one sentence. |
| Level 1 — Explorer | I can evaluate my current platform against the pattern language — for each pattern, I can describe how it is (or is not) present in our platform, and where the gaps are. |
| Level 2 — Designer | I can design platform features using the pattern language. When I design a new capability, I consciously select which patterns apply, how they interact, and where tensions between patterns need to be resolved. I can facilitate co-design workshops with developers to validate pattern choices. |
| Level 3 — Engineer | I can engineer and ship pattern-based improvements incrementally — delivering the smallest viable slice of a pattern, measuring its impact, and iterating. I understand how patterns compose in practice, not just in theory. |
| Level 4 — Steward | I can evolve and extend the pattern language for my organisation — identifying new patterns that emerge from our experience, refining existing patterns based on evidence, and governing how patterns are applied across teams. |

## Feedback and Measurement

*Can you build the feedback loops that allow the platform to learn and improve?*

| Level | Descriptor |
| ----- | ---------- |
| Level 0 — Aware | I understand that platforms without feedback loops stagnate. I can articulate why measurement matters even if I do not yet have measurement practices in place. |
| Level 1 — Explorer | I can map existing feedback loops (OODA loops) in my platform and identify where they are slow, broken, or missing entirely. I understand the difference between lagging indicators (something already happened) and leading indicators (something is about to happen). |
| Level 2 — Designer | I can design feedback loops into platform capabilities — I know where to instrument, what to measure, and how to close the loop so that data leads to action rather than sitting in a dashboard. |
| Level 3 — Engineer | I can operate a platform scorecard that tracks both quantitative and qualitative health. I run continuous discovery practices and experiment-driven improvement. I use measurement to make decisions, not just to report status. |
| Level 4 — Steward | I can embed feedback and measurement as organisational practice — teams across the organisation use measurement to drive platform decisions without my direct involvement. The measurement culture sustains itself. |

## Strategic Thinking

*Can you navigate the strategic dimensions of platform engineering — technology
evolution, organisational dynamics, investment justification?*

| Level | Descriptor |
| ----- | ---------- |
| Level 0 — Aware | I understand that platform decisions have strategic implications beyond the immediate technical choice. I can articulate that "buy vs build" and "which technology" are strategy questions, not just engineering questions. |
| Level 1 — Explorer | I can use Wardley Mapping for situational awareness — positioning platform components by their evolution stage and understanding how that affects build/buy/partner decisions. |
| Level 2 — Designer | I can translate strategic insight into design decisions — I can show how a component's position on a Wardley Map influenced the level of abstraction, the integration approach, or the build/buy choice. |
| Level 3 — Engineer | I can make and communicate strategic technology decisions to non-technical stakeholders. I use Wardley Mapping to plan 3–5 year technology evolution and can justify platform investment in business terms. |
| Level 4 — Steward | I can steward multi-year platform strategy across organisational boundaries — coordinating multiple platforms, navigating leadership changes, and maintaining strategic coherence over time even when priorities shift. |

## Human and Cultural Dimensions

*Can you navigate the human side of platform engineering — adoption, empathy,
teaching, culture?*

| Level | Descriptor |
| ----- | ---------- |
| Level 0 — Aware | I understand that platform success depends on people, not just technology. I can articulate that a technically excellent platform that nobody adopts has failed. |
| Level 1 — Explorer | I can conduct empathy-driven exploration — developer interviews, shadowing sessions, journey mapping — to understand how developers actually experience the platform, rather than how I assume they experience it. |
| Level 2 — Designer | I can co-design with developers and facilitate collaborative workshops. I design *with* developers rather than *for* them. I can translate what I learn from exploration into platform designs that reflect real needs, not assumed ones. |
| Level 3 — Engineer | I can design adoption strategies that address both rational and emotional dimensions — using the Elephant and Rider framework to understand that developers adopt platforms because they *want* to, not because they are told to. I navigate organisational politics and build coalitions for platform investment. |
| Level 4 — Steward | I can mentor others through earlier literacy levels and see their growth over time. I teach the framework and build a community of practice. When I solve a platform problem, I instinctively ask "who else needs to understand this?" and share the learning, not just the solution. |
